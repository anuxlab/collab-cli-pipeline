# Diagnosis and optimization plan for runs 41168974567 and 41169474521

## Evidence inspected

Both runs used `qwen2.5-coder:7b-instruct-q4_K_M`, Ollama local inference, 4 CPU cores, no GPU, 2,048 context, 1,200 max output tokens, and the `all` task set. Both were manually cancelled during the progressive notebook benchmark. Neither reached the later LangGraph agent step.

|---|---:|---:|---:|---|
| 41168974567 | 04:35:12 | 05:48:19 | ~73 min | Enabled |
| 41169474521 | 04:42:51 | 05:48:46 | ~66 min | Disabled |

The model pull and verification completed successfully. The resource gate reported about 14 GiB available RAM and 81–82 GiB free disk. The runner had 4 CPU cores and no GPU. Therefore, these runs were not blocked by the earlier Docker CID-file failure; task reports show Docker execution was reached.

## Why they took so long

The benchmark was configured for all seven tasks and `--max-repairs 2`. That means up to three full model generations per task: as many as 21 generations per baseline phase. The captured artifacts contain six task reports, generally with three attempts per task, and the seventh task was not completed before cancellation.

Observed per-attempt wall-clock durations were roughly 96–355 seconds. Across six tasks, the reports show approximately 18 generation-and-execution attempts per run. This accounts for most of the 66–73 minute duration. It is CPU inference latency multiplied by an overly large experiment budget, not evidence that the model daemon or Docker is hung.

The DSPy-enabled run had not progressed beyond the baseline task reports when cancelled. DSPy optimization is downstream of baseline execution, and the workflow intentionally requires successful baseline evidence before optimizing. Enabling it does not make the baseline faster; it can add more model calls later.

## Comparison with the earlier successful run

Run `40991943449` used Qwen2.5-Coder 14B Q4_K_S for one focused breast-cancer classification task. It completed one model call in approximately 172.6 seconds (325 output tokens, ~2.63 tokens/second), then Docker execution completed in approximately 1.98 seconds. The output achieved accuracy 0.9860, precision 0.9889, recall 0.9889 and F1 0.9889 on 143 test samples.

That successful run had one focused task and one generation. The recent notebook experiments attempted a much broader seven-task suite with repeated repairs. The comparison is therefore primarily about workload size, not proof that the 14B model is faster or inherently better.

## Quality findings from the cancelled runs

- The Python fundamentals task reached a score of 78 after a later attempt in both runs, but needed multiple generations.
- The EDA task repeatedly failed execution; the captured error reports include a read-only Matplotlib config path and other code/runtime problems.
- Classification and NLP outputs encountered missing `seaborn` dependency errors in some attempts.
- Regression produced a syntax error (`key` keyword repeated) and subsequent attempts did not resolve it.
- Time-series execution sometimes returned near-zero error (around 1e-13), a suspicious result requiring leakage review; the emitted result also used a task ID that did not match the benchmark's expected ID.
- Several task reports show that additional repair generations did not improve the score. Repeating a full-code generation after every failure is an expensive and weak repair strategy.

The memory monitor reported zero model-runner RSS and no cgroup reading despite thousands of samples. Those memory numbers are not valid evidence of low model memory; the monitor's process matching / cgroup detection needs a separate correction before memory conclusions can be drawn.

## Changes in this optimized package

1. The Qwen 7B workflow now defaults to the `simple` task set (two tasks) rather than `all` (seven tasks). `all` remains selectable manually.
2. A `notebook_max_repairs` input was added; default is one repair (at most two generations per task), with zero and two still selectable.
3. The notebook generation cap was reduced from 1,200 to 900 tokens to bound long outputs while retaining room for useful code.
4. Qwen 7B runs are serialized per Git ref rather than using a unique concurrency group per run, avoiding accidental simultaneous heavyweight experiments in this workflow.
5. Notebook attempt reports now record model-call wall time and Ollama token/timing metadata, so future runs can separate prefill, generation, and execution costs.

## Recommended experiment sequence

- Smoke test: `notebook_task_set=simple`, `notebook_max_repairs=1`, DSPy off. Expect at most four generations for the two tasks.
- Focused quality test: choose one task ID in a dedicated local invocation or use the `complex` set only after the smoke test works.
- Full baseline: `all`, one repair maximum, DSPy off. Do this only when the smoke test's model-call timings and sandbox behavior are healthy.
- DSPy study: run only after the full baseline produces at least two genuinely executed, structured-result-valid notebooks. Keep the held-out split and seed fixed for paired comparison.
- Do not combine the full benchmark and the separate LangGraph agent run in one long job unless that combined experiment is explicitly desired.

## Validation status

The changes in this package are source-level optimizations. They must be committed to the repository and run through GitHub Actions before claiming the new workflow is validated on hosted runners. All workflows remain `workflow_dispatch` only; no push, pull-request, or scheduled trigger is introduced.
